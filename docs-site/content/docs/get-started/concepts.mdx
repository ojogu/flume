# Concepts

Flume's model has four parts: a **source**, a **pipeline** of operations
run as a **job**, and a **result** you download.

## Source

The **source** is the input media. It is described by a small object:

```json
{
  "type": "video",
  "uri": "https://storage.example.com/video.mp4"
}
```

| Field | Description |
|-------|-------------|
| `type` | `video` or `audio` |
| `uri` | A public `http(s)` URL, or an `uploads/` path returned by the upload API |
| `format` | Format preference — `best` (default), `smallest`, or a resolution (`480p`, `720p`, `1080p`, `4k`). Resolutions are only valid for video sources. |
| `selection` | For playlists — pick specific entries by 1-indexed position, e.g. `{ "entries": [1, 3] }` |

`uri` is optional: a `join` pipeline takes its inputs from the operation's
`clips` param instead, and a job with no pipeline (download-only) also has
no required URI logic of its own.

## Pipeline

A **pipeline** is an ordered list of operations applied to the source:

```json
"pipeline": [
  { "operation": "trim", "params": { "start": "0:00", "end": "0:30" } },
  { "operation": "compress", "params": { "quality": "medium" } }
]
```

| Field | Type | Description |
|-------|------|-------------|
| `operation` | string | An operation name from the registry (see below) |
| `params` | object | Configuration for this operation — optional if the operation has defaults |

Rules:

1. **Steps run in order.** Step 0 runs first, then step 1, and so on.
2. **The output of step N feeds step N+1.** You don't wire steps together;
   Flume does.
3. **An implicit `download` step is prepended as step 0.** Flume fetches
   the source before running your operations.
4. **Adjacent steps must be type-compatible.** Each operation declares the
   artifact types it accepts and produces; a step's output type must be
   accepted by the next step's input types. This is validated at submission
   time.

<Callout title="Download-only jobs">
The `pipeline` field is optional. A job with no pipeline simply downloads
the source file. Most jobs have at least one operation.
</Callout>

## Operation

An **operation** is one processing step from the registry. There are 13
operations across 3 categories:

| Category | Behavior | Operations |
|----------|----------|------------|
| Transformative | One input, one output of the same media type | `trim`, `cut`, `compress`, `transcode`, `resize`, `watermark`, `subtitle`, `mute`, `meme` |
| Combinatory | Multiple inputs merged into one output | `join` |
| Conversion | Changes the media type (video → audio, video → image) | `extract_audio`, `thumbnail`, `gif` |

Each operation declares what it consumes, what it produces, and which
params it accepts:

- **input types** — `video`, `audio`, and/or `image`
- **output types** — `video`, `audio`, `image`, or `gif`
- **params** — name, type, required/optional, default, and bounds

For example, `extract_audio` accepts `video` and produces `audio`; `mute`
accepts `video` and produces `video`; `thumbnail` accepts `video` and
produces `image`. A step that produces `image` can only be followed by a
step that accepts `image`.

> The category labels are descriptive and do not constrain pipeline
> placement. The only structural rule is type compatibility between
> adjacent steps.

The full registry — every operation, param, default, and bound — is
documented in the Operations reference.

## Artifact

An **artifact** is a typed file produced by a pipeline step:

| Type | Produced by |
|------|-------------|
| `video` | Most transformative operations |
| `audio` | `extract_audio` |
| `image` | `thumbnail` |
| `gif` | `gif` |

The final artifact is delivered according to the job's `outputs` field,
which defaults to `[{ "type": "generate_download_link" }]`.

## Job

A **job** is a submitted request — the source, pipeline, and outputs,
persisted with an id and lifecycle status.

Jobs are created with `POST /v1/job` and are **asynchronous**: creation
returns immediately with the job's id, and processing happens in the
background. A job moves through these statuses:

| Status | Meaning |
|--------|---------|
| `pending` | Created, waiting for a worker |
| `processing` | A worker is running the pipeline |
| `succeeded` | All steps finished successfully |
| `partial_success` | Some steps succeeded, some did not |
| `failed` | A step encountered an error |
| `dead` | The job could not run (e.g. exceeded a retry limit) |

You discover the final status by polling `GET /v1/job/{id}`, and each step
in the response carries its own status (`pending`, `running`, `complete`,
`failed`). You can also be notified of lifecycle changes via
[webhooks](/docs/webhooks) instead of polling.

## Result

When a job reaches `succeeded`, its final artifact is ready. With the
default `generate_download_link` output, you download it from:

```
GET /v1/job/{job_id}/download
```

This returns a `302` redirect to a presigned URL for the artifact.

## Webhooks

Webhooks let Flume call your endpoint when things happen. You create a
subscription with a URL and a list of events; Flume signs each delivery
with an HMAC secret so you can verify it came from Flume.

Events cover the job lifecycle (`job.created`, `job.processing`,
`job.completed`, `job.failed`, `job.cancelled`, `job.retried`) and step
lifecycle (`step.started`, `step.completed`, `step.failed`). See
[Webhooks](/docs/webhooks) for the full catalog.

## Validation

Every job is validated at submission time — before any worker touches it.
If validation fails, the request is rejected with a `400` (or `422` for a
malformed body) and no job is created. Validation runs five gates:

| Gate | What it checks |
|------|----------------|
| 1 — Schema | Request body is well-formed (Pydantic) |
| 2 — Registry | Every operation name exists in the registry |
| 3 — Params | Required params present, types correct, values in bounds |
| 4 — Type compatibility | Source type matches step 0; each step's output is accepted by the next step |
| 5 — Pipeline spec | Enriched spec is built and stored |

The error envelope and the messages each gate produces are documented in
the Errors reference.
